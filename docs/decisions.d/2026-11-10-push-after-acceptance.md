## Шаг 1: манифест вместо `git add -A`, читаемое сообщение коммита

- **`git add -A` удалён из обоих путей** (`grep 'execSync("git add -A"'` → 0).
  Стейджинг теперь идёт строго из манифеста: `artifactFileList(taskText,
  resultText)` — сначала строка `MANIFEST:` / `FILES:` / `ARTIFACTS:` из брифа,
  иначе пути из текста отчёта агента (в бэктиках или после `File(s)/Path/
  Created/Modified/Added:`). Кандидаты фильтруются по факту существования
  файла (`existingFilesIn`, `statSync(...).isFile()`), а отсекаются заранее:
  `..`, `*`/`?`, ведущий `-`, длина `>400`, завершающий `/` (каталог).
- **Сообщение коммита** = `task <N>: <title>`, где `title` — первая
  содержательная строка брифа без маркерных блоков (`briefTitle`, до 72
  символов). Причина: в `plexus-doc` от машинной подписи остались коммиты вида
  `task 172: ?? notes/` и `task 164: M canon/content/bundle-language.md`.
- Пустое дерево и пуш без верификации больше не дают `готова`: правило FIX 1 и
  FIX 2 сохранены (`commitReachedOrigin` читает ref у origin и сравнивает).

## Шаг 2: Acceptance Gate (Вариант А)

Вариант А выбран, потому что раннер GitHub Actions эфемерен: локальный коммит,
ждущий приёмки между прогонами, умирает вместе с раннером — «ждать из Turso»
может только живой процесс, поэтому цикл ожидания внутри этого же прогона
(переиспользуя запланированную механику `[JOINT]`/`awaiting_human`, BACKLOG
п.35).

Порядок в `run()`:

1. `doWork` отработал; **гвард решает первым** — просить основателя принять
   пустое дерево значит снова открыть лазейку (этим занимался
   `uploadTaskCheckpointsAndArtifacts` при пустом дереве);
2. `stageTaskArtifacts()` — локальный коммит, **без пуша**;
3. строка переводится в статус `ждёт_приёмки` (этого статута нет в `SELECT`
   диспетчера, который берёт только `ожидает` и `провал`, поэтому задачу
   нельзя перехватить на ходу) + уведомление автору в Telegram;
4. `waitForAcceptance()` — опрос строки до `ACCEPTANCE_WINDOW_MINUTES` (по
   умолчанию 90, `ACCEPTANCE_POLL_MS` 30 с):
   - `принята` → `pushAcceptedArtifacts()` (пуш + `commitReachedOrigin`) →
     `готова`; провал пуша после приёмки → `провал` (retryable, работа локальна);
   - `отклонена` / истёкшее окно / строка ушла сама → `rollbackLocalWork()`
     (`git reset --hard <preWorkSha>`, без `git clean` намеренно) →
     `провал_фатальный`, без retry-метаданных;
5. вердикт гейта не проходит через `classifyFailure`: решение принимает
   человек, поэтому `status` считается явно, а не по сообщению провайдера.

Compute-путь (`executeLongCompute` → `uploadTaskCheckpointsAndArtifacts`,
1521/1556) больше **не пушит сам**: он коммитит локально из манифеста
(чекпойнт-файлы, которые сам скопировал, + манифест задачи), а пуш делает
гейт после приёмки — это закрывает второй неверифицируемый пуш.

Аварийное освобождение (`releaseStuckTaskAfterCrash`) теперь снимает и
`выполняется`, и `ждёт_приёмки` — падение во время ожидания не оставляет
нового класса зомби.

## Чего в этой реализации ещё нет (открыто, не закрыто)

- **Писателя `принята` нет.** Статус никем не выставляется: `worker/index.js`
  обрабатывает только `/start` и `dispatch`, обработчика `callback_query`/
  кнопки приёмки в нём нет. До появления кнопки решение пишется только руками
  (`UPDATE tasks SET status='принята' WHERE id=N`). Это и есть недостающая
  половина механизма — каркас вооружён, но вызвать его пока некому.
- **Окно приёмки против job cap.** Окно по умолчанию 90 мин, кап прогона тоже
  90 мин: при долгой работе ожидание обрежется раннером, и гвард запишет
  `провал` (retryable). Оба значения переопределяются через окружение.
- **Пуш агента не снят**: `dsh` под `danger-full-access` (`:3461`) может
  запушить во время работы. Барьер пока организационный; снятие пуша у агента
  (read-only кред или временный `pre-push` hook) — отдельная задача.
- **Приёмка выполнителя не пройдена**: провайдер (openrouter free) отдаёт 429
  `free-models-per-day` и 403 на авторизации, живой прогон под гейтом сейчас
  недоступен. Правило Infrastructure Acceptance требует 3 задачи подряд без
  ошибок провайдеров — после восстановления квоты.

## Локально-облачный паритет

Локальный контур (`queue.sh`) не пушит вовсе — у его репозитория нет remote по
правилу родительского `AGENTS.md` — поэтому pre-acceptance пуша, который
нужно было бы закрыть, там не существует. Расхождение названо, а не устранено:
локальная приёмка — это QA/чек-лист, облачная — статус `принята` в Turso.
Симметричное изменение здесь означает не «повторять пуш», а «зафиксировать
разные механизмы приёмки».

## 2026-11-10 (дополнение): закрыты три блокера Acceptance Gate

По замечаниям Плексуса, до тестирования. Коммит: см. `git log` родительского
`queue-engine` (`fix(executor): resolve acceptance gate blockers`).

**Блокер 1 — окно приёмки против job cap.** Теперь имена, а не числа в
комментариях: `JOB_CAP_MINUTES = 180`, `ACCEPTANCE_WINDOW_MINUTES = 60`
(`scripts/executor.mjs`). Арифметика основателя: самая долгая единица работы
~120 минут, 180 − 120 = 60 — окно уцелеет и при ней. `executor.yml`
(`timeout-minutes`) поднят 90 → 180: GitHub убивает джоб там, что ни говорит
JS, поэтому постоянная, которой нет в workflow'е, — не постоянная.

**Блокер 2 — пуш агентом в обход гейта.** `dsh` работает под
`danger-full-access` и может закоммитить и запушить сам. Правило: коммит
агента — законный артефакт, но его файлы обязаны быть объявлены в манифесте
**брифа** (`MANIFEST:`/`FILES:`) — не в отчёте агента: проверка, которую агент
удовлетворяет собственными словами, проверкой не является. Нарушение →
`AGENT-PUSHED-OUTSIDE-MANIFEST` + `rollbackLocalWork()`. Если коммит успел
лечь на origin, причина называет это прямо: `rollbackLocalWork()` сбрасывает
локальное дерево, но не отзывает коммит с GitHub. Манифест разделён на
`briefManifest()` и `reportFileList()` именно ради этого вопроса (объединённый
`artifactFileList()` остался для стейджинга).

**Блокер 3 — просроченное окно не равно отклонению.** Таймаут больше не даёт
откат и `провал_фатальный`: строка уходит в собственный статус
`ждёт_приёмки_просрочено`, работа остаётся как есть, retry-метаданные не
пишутся. Причина: молчание — не решение, а работа может быть правильной и
просто неотосмотренной; уничтожать её по ничему не ответившему нельзя.
`DISPATCH_SELECT_SQL` теперь содержит явное
`status NOT IN ('ждёт_приёмки', 'ждёт_приёмки_просрочено')` — защита от
расширения allowlist'а в будущем. Маппинг вердикта гейта вынесен в
`gateVerdict()` и покрывается тестами.

**Неimplemented (намеренно, требует решения):** раннер эфемерный, поэтому
локальный коммит умирает вместе с прогоном. Два варианта сохранения — пуш в
`task/<N>` до таймаута (это пуш без приёмки, ровно то, что гейт запрещает) и
запись патча в Turso (нужна колонка/ключ, которого нет) — оба принадлежат не
гейту. Сейчас сохраняется след: sha коммита, ветка, список файлов, sha начала
прохода.

**Тесты:** `tests/commit-verification.mjs` 31/31, `tests/acceptance-gate.mjs`
57/57 (группы L — постоянные и согласие workflow'а, M — манифест агента,
N — просроченное окно, K4 — явное исключение диспетчера).

## 2026-11-10 (дополнение 2): сохранение работы при таймауте — `pending/task-<id>`

Решение основателя по открытому вопросу из предыдущего дополнения: при
истечении окна приёмки работа не только остаётся без откатa, но и **сохраняется**
пушем в собственную ссылку `pending/task-<id>` (`pendingBranchName()`,
`pushPendingBranch()`, вызов на пути таймаута в `run()`).

Ключевое ограничение, записанное в коде и проверенное тестом: это единственное
место, где пуш идёт без приёмки, поэтому он не пишет в целевую ветку вообще —
`pending/` это другое пространство имён. Отказ по-прежнему откатывает работу и не
пушит ничего (тесты O12-O13). Сохранение нетрудно потерять: если пуш в `pending`
не удался, строка всё равно становится `ждёт_приёмки_просрочено`, а `result`
говорит, что работа НЕ сохранена (раннер эфемерный).

Слияние `pending/task-<id>` в целевую ветку — решение и действие основателя;
полный план в `docs/DECISIONS.md` родительского репо (`PENDING-BRANCH-MERGE`).
Писателя приёмки по-прежнему нет: `worker/index.js` не имеет обработчика
`callback_query`. Тесты: группа O в `tests/acceptance-gate.mjs` (70/70),
`tests/commit-verification.mjs` 31/31.

## 2026-11-10 (дополнение 3): гейт стал стандартом для всех репозиториев

По briefу основателя 2026-11-10: «механизм приёмки — это стандарт для всех
проектов». Новая спека — `docs/ACCEPTANCE-GATE-SPEC.md` (принцип, что копировать,
что настроить, как работает, как запросить внедрение); правило уровня проекта —
раздел 4a в `AGENTS.md` этого контура.

- **`scripts/accept-pending.mjs`** — универсальный скрипт приёмки:
  `<taskId> <targetRepoPath> <targetBranch> [pendingBranch]`, читает Turso из
  окружения, поэтому запускается из любого репозитория. Барьер статуса
  `принята` стоит ПЕРВЫМ шагом (всё остальное — fetch, checkout, merge --no-ff,
  push, верификация, `готова`, удаление pending-ref). Коды выхода различены:
  `MERGE-CONFLICT` (4) — мерж отменён, ничего не запушено и строка не закрыта;
  `WORKDIR-DIRTY` (3) — в целевом дереве есть незакоммиченная работа;
  `NOT-ACCEPTED` (2) — решения нет или оно отозвано; `PUSH-NOT-VERIFIED` (5) —
  пуш вышел 0, но ref не сдвинулся.
- **`scripts/list-accepted-pending.mjs`** — выборка строк к мержу
  (`status='принята'` + `metadata.pending_branch`); это половина «найти задачи»
  из брифа, вторая половина — сам accept-pending.
- **`.github/workflows/merge-pending.yml`** — cron */5, один мерж за раз
  (concurrency), целевой репо через `vars.TARGET_REPO`. Статус, изменившийся
  после выборки (exit 2), прогон не валит; `MERGE-CONFLICT` (4) и прочие
  фатальные — нет.
- **`scripts/executor.mjs`** при просроченном окне теперь пишет
  `metadata.pending_branch` и `metadata.target_branch`: сохранение полезно только
  если его можно найти, а разбор `result` текстом — проверка, которая живёт до
  первой правки предложения.
- Тесты: `tests/accept-pending.mjs` 34/34 — счастливый путь с реальшим мерж-узлом
  (форма вызова workflow'а: свежий checkout), конфликт, все не-`принята`
  статусы, отсутствующая строка, грязное дерево, absent pending-ref, пуш,
  который «успел», а ref не сдвинулся, маскирование секретов. Тестовые репозитории
  временные, настоящие репозитории не трогаются.
- Спека и правило зафиксированы как Spec-First: репозиторий не считается
  подключённым без четырёх пунктов Adoption (файлы, три секрета
  `TURSO_URL`/`TURSO_TOKEN`/`REPO_TOKEN`, запись `metadata` при парковке,
  поведение `list-accepted-pending.mjs`).
- Живой прогон по-прежнему невозможен: провайдеры отдают 429/403, приёмка
  Infrastructure Acceptance открыта; проверено исполнением на временных
  репозиториях, не на живом прогоне.
